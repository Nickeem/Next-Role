# Development

## Setup

```bash
uv sync                     # creates .venv with runtime + dev dependencies (Python 3.12)
cp .env.example .env        # then set NEXT_ROLE_API_KEY and database credentials
```

## Running locally without Docker for the API

```bash
docker compose up -d db                     # or any PostgreSQL 16 instance
uv run alembic upgrade head                 # uses NEXT_ROLE_DATABASE_URL from the environment
uv run uvicorn next_role.main:create_app --factory --reload
```

The app reads `.env` from the working directory. Alembic does not: it reads
`NEXT_ROLE_DATABASE_URL` from the process environment only, so export it or prefix the
command (`NEXT_ROLE_DATABASE_URL=... uv run alembic upgrade head`). If unset, Alembic falls
back to `postgresql+psycopg://next_role:next_role@localhost:5432/next_role`.

## Tests

Integration tests need a disposable PostgreSQL. The test fixtures **downgrade the schema to
base and truncate every table**, so never point them at a real database.

```bash
docker compose -f docker-compose.test.yml up -d --wait   # PostgreSQL on 127.0.0.1:5433
uv run pytest                                            # unit + integration
uv run pytest tests/unit                                 # no database needed
TEST_DATABASE_URL=postgresql+psycopg://... uv run pytest  # use another disposable database
```

If the test database is unreachable, the integration tests are **skipped**, not failed.
pytest's summary reports them. Tests are deterministic: assessments pass an explicit `as_of`
date, and LLM providers are faked, with HTTP mocked through `httpx.MockTransport`.

Test layout:

- `tests/unit/`: pure logic (skills, extraction, matching engine, LLM extraction and
  adapters, configuration).
- `tests/integration/`: the API over a real database (candidates, jobs, assessments,
  including the end-to-end scenario), migrations, and health checks.

### PDF rendering tests

Chromium only runs in the renderer image (Playwright does not support every host OS), so the
PDF tests are marked `renderer` and skipped elsewhere. Run them in the image:

```bash
docker build --target renderer -t next-role-renderer .
docker run --rm --user 0 -v "$PWD/tests:/app/tests:ro" next-role-renderer \
    sh -c "uv pip install -q --python /opt/venv/bin/python pytest && pytest -m renderer"
```

## Quality checks

Run all of these before opening a PR:

```bash
uv run ruff format --check .
uv run ruff check .
uv run mypy                 # strict, on src/
uv run pytest
```

## Frontend

The web workspace is a Vite + React + TypeScript app in `frontend/` (ADR 0005). Node 22.

```bash
cd frontend
npm ci
npm run dev          # http://localhost:5173, proxies /api to http://localhost:8000
npm run typecheck
npm test             # vitest + Testing Library, fetch mocked
npm run build        # frontend/dist
```

For the dev server, run the API with `NEXT_ROLE_UI_PASSWORD` set and sign in through the UI.
To serve a build from FastAPI locally, set `NEXT_ROLE_STATIC_DIR=frontend/dist`. The Docker
image builds the frontend in a Node stage and sets this automatically.

`src/types.ts` mirrors the API schemas, and `labels.ts` mirrors
`review.workflow.overrides_assessment`; `labels.test.ts` uses the same cases as the Python
test, so keep both in sync when the rules change.

## Migrations

```bash
export NEXT_ROLE_DATABASE_URL=postgresql+psycopg://next_role:next_role@localhost:5433/next_role_test
uv run alembic upgrade head
uv run alembic revision --autogenerate -m "describe change" --rev-id 0005_short_name
uv run alembic downgrade -1
```

Review every autogenerated migration. One known quirk: enums are stored as constrained
strings (`native_enum=False, create_constraint=True`), and autogenerate emits each CHECK
constraint twice. Keep only the explicitly named `op.f("ck_...")` constraints, and set
`create_constraint=False` on the `sa.Enum(...)` columns inside the migration.
`tests/integration/test_migrations.py` round-trips all migrations and fails if the models and
the migrated schema differ.

## Conventions

- Follow `AGENTS.md`: work on a feature branch, use conventional commits, and open a PR.
  Never commit secrets or real candidate data.
- Domain services take a `Session` and Pydantic models, and raise `next_role.errors`
  exceptions. Routes stay thin.
- Changes to matching rules must update `docs/matching.md` and bump
  `matching.engine.METHOD_VERSION`.
- Use only synthetic data in examples and fixtures (`examples/`).
